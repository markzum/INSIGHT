# Метрики качества

Модель не дообучается на отзывах. Сигнал копится в SQLite и в ручной разметке, а в следующий прогон попадает правка конфига или промпта `v1`, с новой версией файла, если меняется инструкция.

## Что считаем

- **Precision@k релевантности.** На ручной разметке пар «клиент, кластер» доля кластеров из top-k, которые эксперт счёл значимыми. Считается по `relevance_score` до LLM, чтобы отделить отбор от формулировки.
- **Доля утверждений с живым источником.** У факта, риска, возможности и пункта «почему это важно» каждый `source_id` есть среди источников запуска. Это уже проверяет `verifier` на каждом прогоне; метрика — доля инсайтов без замечания `source_id`.
- **Доля `ok` с первой проверки.** `verifications[0].decision == ok`. Падение доли — повод смотреть, не пустой ли `bank_view` и не отсекает ли проверка числа.
- **Фактические ошибки на выборке.** Эксперт отмечает выдуманное число, неверную отрасль, чужого контрагента, пересказ без связи с клиентом. Цель — ноль выдуманных чисел: проверка не пропускает число, которого нет в источнике.
- **Оценка экспертов.** Короткая шкала по шести вопросам кейса: факт, связь с компанией, последствия, действие, позиция банка, источники. Отдельно: понятно ли, где банк, а где модель.
- **Отзыв пользователя.** `POST /agent/feedback` с `useful: true|false` и необязательным комментарием. Считается доля полезных по `insight_id`. Разбор неполезных идёт по отрасли и фактору из trace. Если один и тот же тип формулировок стабильно бесполезен, правило или фраза добавляются в `config/sensitivity_rules.yaml` либо в промпт следующей версии. Веса скоринга из этого автоматически не пересчитываются.

## Как смотреть прогон

В trace уже есть план, инструменты, черновики, решение проверки, признаки и источники. Для выборки достаточно выгрузить эти объекты и посчитать доли выше. Отдельного дашборда в прототипе нет.
