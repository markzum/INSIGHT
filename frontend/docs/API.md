# Данные и граница API

## Статус контракта

`data/demo.json` — вручную подготовленный fixture версии `3.0`, а не сохраненный ответ существующего бэкенда. `types.d.ts` описывает его структуру. Поля `is_demo: true`, `verification_status: "demo_only"`, `ai_interpretation.status: "prewritten_demo"` и `bank_view.status: "not_loaded"` обязательны для текущих тестовых материалов.

Фронтенд имеет точки подключения API, но рабочий сервер, аутентификация, парсер, поиск и LLM не входят в поставку. Переключение `apiBaseUrl` само по себе не превращает fixture в проверенную аналитику.

Текущий интерфейс оптимизирован для fixture: ряд подписей источников, профиля, готовности анализа и этапов процесса остаются демонстрационными. API-адаптер позволяет проверить обмен данными, но еще не является производственным режимом для реальных материалов. До его использования нужно согласовать контракт и представление всех реальных статусов, дат, источников и банковской позиции.

## Настройка

```js
window.ALFA_CONFIG = {
  apiBaseUrl: '',
  requestTimeoutMs: 10000
};
```

Пустой адрес означает локальный режим. Для сервера используйте HTTPS и явно настроенный origin. Не передавайте ключи модели, сервисные токены или секреты в этой конфигурации.

## Получение рабочего пространства

```http
GET {apiBaseUrl}/workspace?company_id={companyId}&role={roleId}
Accept: application/json
```

Параметры обозначают выбранный контекст. Сервер должен проверять, что пользователь имеет право читать компанию и запрошенную роль; входные значения из браузера не являются подтверждением прав.

Демонстрационные роли: `financial_director` — финансовый директор, `ceo` — генеральный директор, `treasurer` — казначей.

Ответ `200` содержит объект dataset v3:

```json
{
  "schema_version": "3.0",
  "is_demo": true,
  "as_of": "2026-10-22T09:00:00+03:00",
  "disclaimer": "Синтетические данные для демонстрации",
  "companies": [],
  "events": []
}
```

Пример показывает контейнер, а не полноценный демонстрационный профиль. Рабочие записи находятся в `data/demo.json`. Пустой `events` означает успешную загрузку без событий; это не сетевой сбой. Компания должна сохраняться в контексте даже при пустой ленте.

| Объект | Смысл |
| --- | --- |
| `companies[].features` | Признаки клиента с именем поля, читаемой меткой, значением, единицей и происхождением |
| `companies[].missing_data` | Известные пробелы профиля; отсутствие признака не означает отрицательное значение |
| `events[].company_ids` | Синтетические компании, для которых подготовлен пример |
| `events[].relevance[companyId]` | Демооценка, причина значимости, использованные признаки и персональное резюме; `role_scores` и `role_summary` задают различия по роли |
| `facts` | Утверждения из демоисточника, ссылка на материал и подтверждающий фрагмент |
| `bank_view` | Отдельная позиция банка; в fixture только отсутствие материала |
| `ai_interpretation` | Подготовленная демонстрационная интерпретация, условия, допущения, риски и возможности |
| `actions` | Возможные следующие шаги, роль исполнителя, проверки перед действием и основания |
| `sources` | Именованные демонстрационные материалы; `url: null`, поскольку оригинала в интернете нет |
| `verification`, `missing_data`, `analysis_status` | Противоречия, пробелы и неполнота анализа |
| `suggested_questions` | Заранее подготовленные пары вопрос–ответ |

`basis.fact_ids` ссылается на факты того же события, `basis.company_feature_refs` — на поля выбранной компании, `basis.bank_source_ids` — на действительно использованные банковские материалы. Нельзя создавать фиктивную ссылку только для заполнения блока. Все идентификаторы должны быть устойчивыми и уникальными в своей области.

Приоритет и score в demo — редакционные оценки, не вероятность, не финансовый прогноз и не измеренная точность AI. `reasoning_steps` содержит проверяемые промежуточные результаты для показа пользователю; это не скрытые рассуждения модели.

## Уточняющий вопрос

```http
POST {apiBaseUrl}/insights/{insightId}/questions
Content-Type: application/json
```

```json
{
  "company_id": "company-id",
  "role": "role-id",
  "question": "Каких данных не хватает для оценки влияния?"
}
```

```json
{
  "answer": "Текст ответа с явными ограничениями и основаниями.",
  "is_demo": true,
  "source_ids": []
}
```

`answer` — текст, а не HTML. `is_demo` должен быть явным: отсутствие метки не подтверждает реальную генерацию. `source_ids` должны разрешаться в доступные пользователю материалы. Ссылки на источники и статус ответа необходимо сохранять вместе с текстом; источник, которого пользователь не вправе видеть, нельзя раскрывать через ответ.

В локальном режиме отправка вопроса не вызывает модель: предлагаемые вопросы показывают подписанные подготовленные ответы. Для вопроса вне fixture требуется честное сообщение о необходимости серверной интеграции.

## Ошибки и переход к реальному API

Сервер должен возвращать соответствующий HTTP-статус: `400` для неверного запроса, `401` для отсутствия сессии, `403` для отказа в доступе, `404` для недоступного события, `429` для ограничения нагрузки и `5xx` для сбоя. Пользователь должен иметь возможность повторить запрос, не потеряв введенный вопрос. Таймаут задается `requestTimeoutMs`.

Перед подачей реальных данных требуется расширить и версионировать контракт: добавить проверенные статусы фактов, реальные URL и документы, состояние загрузки банковской аналитики, авторство и дату ее публикации, версии профиля и анализа, фактические trace-результаты, права на материалы и серверное состояние действий. Текущие литеральные типы fixture намеренно запрещают выдавать демонстрационные материалы за настоящие.

Банковский вывод допустим только со ссылкой на предоставленный и доступный аналитический материал. Сгенерированный текст нельзя маркировать позицией банка. Отсутствующий материал должен сохранять `not_loaded`/эквивалентный явный статус, а не подменяться правдоподобным текстом.

## Предлагаемая серверная схема

```text
Браузер → API / сессия / проверка доступа к компании
             ├─ Профили и связи компаний с правами доступа
             ├─ Новости: сбор → нормализация → дедупликация → факты
             ├─ Банковские документы → индекс поиска / RAG
             ├─ Собственный агент: план → инструменты → проверка → повторный поиск
             ├─ Разрешенные кейсом модели через серверный шлюз
             └─ Журнал источников, версий, действий, качества и обратной связи
```

Клиентский `company_id` не может быть единственной границей изоляции. Проверки доступа должны действовать и внутри поиска/RAG, и при вызове инструментов. Тексты новостей и документов являются недоверенными данными: инструкции внутри них не должны менять полномочия агента или запускать внешние действия. Инструменты ограничиваются необходимыми операциями, обращения журналируются, чувствительные поля минимизируются, а секреты находятся только на сервере.

Маршрутизация моделей должна следовать приложению 3 кейса. Фронтенд не выбирает провайдера и не содержит ключей. Наличие подготовленного trace в интерфейсе не заменяет обязательную самостоятельную реализацию агентной логики.
